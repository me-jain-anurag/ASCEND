In one line

What ASCEND does

ASCEND looks at a small network, finds every way a hacker could climb from a low-access foothold up to the most important machine, actually runs each way to prove it really works, then works out the fewest fixes that block the most routes — and proves the fixes worked.

Scan the machines→ List every break-in route→ Run each route to confirm it→ Pick the cheapest fixes→ Prove the routes are gone

The test network is 3 machines: web01 (entry, low access) → app01 (middle) → db01 (the "crown jewel" database). That last step — proving routes vanish after a fix — is the headline result of the whole project.

Section 1

What is in scope for 7th semester

7th sem is about having one complete, working system that proves itself on the 3-machine Docker lab — with real numbers and the before/after fix proof — written up and shown on the dashboard for the review.

The commitment Make the full loop run end-to-end on the current 3-host lab, produce honest results, prove that the recommended fix removes the attack routes, and present it. Nothing bigger.

Deliberately NOT in 7th sem

The bigger 10-machine network, real virtual machines, a live kernel exploit, the AI prediction model, and the large dataset — all of that is 8th sem on purpose, so this semester stands on its own as a finished, demoable result.

Section 2

What is already built (done)

The hard engineering is finished — the whole machine exists and the pieces work:

  • The practice network — a safe 3-machine Docker lab (web01 → app01 → db01) that rebuilds and resets in seconds.
  • The scanners — read-only probes that look at each machine and record its weaknesses.
  • The route finder — lists every break-in path from the entry point to the database (currently finds 2 distinct routes).
  • The prover (verifier) — actually runs each route and confirms it worked using a hidden "canary" check, not just a guess.
  • The fix engine (chokepoint) — works out the smallest, cheapest set of fixes that blocks the most routes.
  • The dashboard — a screen (FastAPI + React) to see the network, the routes, and the results.
  • 52 automated tests — checks that keep the code honest.
Where we actually stand today: 4 weaknesses found → 2 routes to the database → 1 confirmed real by execution (and 1 partial). The fix engine already ranks fixes: removing the exposed SSH key blocks both routes, the setuid fix blocks 1, and so on. The one part that does not exist yet is the AI scorer — that is 8th-sem work.
Section 3

What is left to finish 7th sem

Almost everything that remains is running the system, capturing the numbers, and writing it up — not building new features. In more detail:

  • Run it for real, once, cleanly — and save the results. Reset the lab to a clean state, run the whole pipeline (scan → find routes → prove each one), and let it write the results file (outcomes.jsonl). That file is empty today, so right now we have no saved, citable numbers. One clean run gives us our real headline: "2 routes found, 1 proven real." Then run it a second time and check we get the same answer — a number a reviewer can trust is one that repeats.
  • Prove the fix works — the before/after loop. Count the routes to the database (2). Apply the single fix the engine recommends (remove the exposed SSH key). Re-run. Show those routes are now gone (2 → 0). Then add two honesty checks: a "negative control" (apply a fix that shouldn't matter and show routes don't drop) and an "order" check (our cheapest-fix order vs the obvious severity order). Wrap it so one command does the whole before→fix→after, live.
  • The exact "best possible" fix check — done. The fix engine picks fixes the quick (greedy) way; an exact solver now runs alongside it, finds the true cheapest fix set by exhaustion, and reports how close greedy gets (greedy is exactly optimal on the current lab). The negative control and the greedy-vs-naive order check are in too. This was the last new code for 7th sem — it is committed and covered by tests; what remains is to show its numbers in the report.
  • Settle one naming choice. Decide how we label the "reused credential" technique — T1550 or T1078.003 — and make the code (scope.yaml), the PDF, and the report all say the same thing. This is the only inconsistency left in the project, and it's a 10-minute decision once we pick one.
  • Turn the results into simple charts and tables. From that one saved run, make four small pictures: routes found vs proven (2 vs 1), before vs after the fix (2 → 0), which fix blocks how many routes (exposed key 2/2, setuid 1/2, …), our fix-order vs the obvious order, and greedy vs best-possible. Also a speed number (how fast it finds the routes). Each one should be generated from the run, not drawn by hand, so it always matches.
  • Show it and write it up. Make the dashboard clearly show the network, the proven routes, and the before/after. Take clean screenshots as a backup. Then write a short review report: what ASCEND is, what we built, the results with the charts, the proof that the fix works, and a short note on what 8th sem will add. Make sure the report, the dashboard and the run all tell the same story.

In short: the system is built — 7th sem is about running it, proving it, and presenting it honestly.

Section 4

8th semester — high level (the bigger, research half)

This is the substantial, harder work we deliberately leave for next semester. High level only:

  • Grow the lab from 3 containers to about 10 machines, including 2 real virtual machines.
  • Run a real kernel exploit (DirtyPipe) on a virtual machine — something containers cannot do today.
  • Build a big labelled dataset — 30+ automatically generated lab variants to learn from.
  • Build the AI "exploitability scorer" — predicts whether a route would work without running it, and must beat simple baselines or be reported honestly.
  • Assessment mode (stretch) — point it at a real machine, read-only, and get ranked fixes.
  • Write the research paper.
Why this split is defensible 7th sem is a complete method proven on a controlled lab — it reviews cleanly on its own even if 8th never happened. 8th is the risky, novel half (real exploitation, a real dataset, an AI model that might not win) — exactly the kind of substantial work a final-year second semester and a paper are meant to carry.
