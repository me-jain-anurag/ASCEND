A simple day-by-day work sheet for four people. We start with only the Docker lab built, and by the end of 10 days the whole system is built, run, proven, and written up — all of 7th-sem done. Each day, each person writes one short status line.

The idea

Where we start and where we finish

For this sheet we pretend only one thing is built — the practice lab. Everything else gets built, run and proven over the 10 days. (In real life more is already done — so just mark those rows done as you go. The sheet is the full story of 7th sem, start to finish.)

Day 0 — what we have

The practice network only. A safe 3-machine Docker lab (web01 → app01 → db01) that rebuilds and resets in seconds.

→
Day 10 — what we'll have
  • Scanners that record each machine's weaknesses
  • Route finder (2 distinct break-in routes to the database)
  • Prover that runs each route and confirms it (1 proven, 1 partial)
  • Fix engine (cheapest fixes that block the most routes)
  • Dashboard showing the network, routes and results
  • 48 automated tests
  • + a clean run, the before/after proof (2→0), charts and the report
How the 10 days flow Days 1–7: build the pieces and get the first full run. Days 8–10: prove the fixes, make the charts and dashboard demo, write the report. The pieces connect in order — scanners feed the route finder, which feeds the prover, which feeds the fix engine and the dashboard — so the days are lined up to match.

P1

Scanners & Route Finder

Builds the "eyes" of the system (what's wrong on each machine) and the "brain" that turns those weaknesses into actual break-in routes.

DayWhat to doWhat to enter in the sheetWhy it matters
1Reset the lab to a clean state and write the first read-only scanners (which SUID programs and sudo rules exist on each machine)."Lab reset; first scanners read web01/app01/db01."The scanners are the eyes — everything starts from the facts they collect.
2Finish the rest of the scanners (exposed keys, which machines can reach which, kernel version, Docker socket). Save one facts file per machine."All scanners done — facts saved per host."Complete, honest facts, so no weakness is missed and none is invented.
3Turn raw facts into real "weaknesses", keeping only the 7 techniques in scope."Weaknesses derived — 4 found across the lab."Cuts the noise down to the few weaknesses that actually matter.
4Build the route finder: search from the entry machine up to the database, step by step."Route finder builds paths web01→db01."This is the brain — it lists every way in, not just single weaknesses.
5Tidy it up: merge duplicate routes, cap depth and path count, report what was cut. 6 raw orderings collapse to 2 distinct routes."Route finder tuned — 2 distinct routes."A trustworthy route count with no double-counting.
6Hand the routes to P2's prover in the right format; fix any mismatches."Routes wired into the prover."The finder and prover must speak the same language to work together.
7Help connect the whole chain — scan → find → prove — and run it once end to end."Scan→find→prove runs end to end."First time the full pipeline flows start to finish.
8On the first real run, sanity-check that the routes make sense."Routes checked sensible on real run."Catch any wrong route before it reaches the report.
9Lock the route finder's behaviour for the final run (same settings, recorded)."Route finder frozen for final run."Stable routes so the report and demo match.
10Help with the final clean run and confirm the route count."Final run — 2 routes confirmed."The number we present is the number the system actually produced.
P2

Prover & Fix Engine

Builds the part that runs each route to prove it really works, and the engine that picks the smallest, cheapest set of fixes.

DayWhat to doWhat to enter in the sheetWhy it matters
1Place the hidden "canary" tokens in the lab and plan how each technique will be run."Canaries placed; prover plan ready."The canary is how we PROVE a route worked instead of guessing.
2Build the first prover: local tricks (sudo rule, SUID program, exposed key)."Local prover works — sudo/SUID/key confirmed."Proves the most common ways to become root on a machine.
3Build the SSH "jump to another machine" prover."Lateral prover works — hops web01→app01."Proves the attacker can really move across machines, not just in theory.
4Make pass/fail depend on the canary, with clear reasons (failed / not applicable / timeout)."Pass/fail by canary works, with reasons."Honest results — a route only counts if the canary actually fires.
5Run the prover over P1's 2 routes and save the results file."First prove run — 1/2 routes confirmed real."The core result of the whole project: proven, not predicted.
6Build the fix engine: find the cheapest set of fixes that blocks the most routes."Fix engine ranks fixes — exposed key blocks 2/2."Turns a list of problems into a clear, cheap action plan.
7Add the exact "best possible" check to compare against the quick (greedy) pick."Greedy vs best-possible compared."Shows our cheap pick is as good as the best option.
8Run the proof loop: apply the top fix, re-run, show the routes vanish."Proof loop works — routes to db01 2→0."Proves the recommended fix actually works in the real lab — the headline.
9Add the two honesty checks: a fix that shouldn't matter (routes unchanged) and our fix-order vs the obvious order."Negative control + order check done."Proves the drop is from the right fix, and our order beats the obvious one.
10Freeze the prover and fix engine for the final run."Prover & fix engine frozen."Nothing changes, so the demo matches the report.

How to use it

Using the tracking sheet

  • Make one tab per person (P1–P4), or one shared tab with a block each.
  • Rows = Day 1 to Day 10. Columns = Task · Status (what to enter) · Done? · Notes.
  • Each day, the owner pastes the short line from the "What to enter" column once the task is done, and ticks Done.
  • Anything already finished in real life — tick it done straight away. The sheet is the full 7th-sem story; it doesn't have to pretend things aren't built.
  • Keep the "Why it matters" note beside each task so whoever you hand the sheet to understands how each day fits the whole system.
One line for whoever you hand this to: starting from just the practice lab, four people spend 10 days building the scanners, route finder, prover, fix engine, dashboard and tests, then running it, proving the fixes work, and writing it up — ending 7th sem with a complete, proven, reproducible result.
