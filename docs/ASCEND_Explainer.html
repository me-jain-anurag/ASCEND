01 — The one sentence

What is ASCEND?

Imagine an attacker who has broken into one unimportant machine on a company's network — say a public web server. The real danger isn't that one machine; it's whether they can climb from there, step by step, all the way to the crown jewel: the database full of customer data.

ASCEND is a tool that maps out every one of those climbing routes, runs each route for real inside a safe practice network to see which ones genuinely work, and then works out the smallest number of fixes that cut off the most routes.

Why the name Ascend literally means to climb — and that is exactly what an attacker does when they go from a low-privilege account up to full control. Each letter is also a real part of the project: Attack-path, Scoring, Chokepoint, Evaluation, for Network Defence.

It is a blue-team (defender's) tool. The whole point is to help a defender fix things before a real attacker finds them. Everything runs inside an isolated practice lab we build ourselves — never against real systems.

02 — Why this is needed

The gap in today's tools

Companies already have security tools. Three common kinds:

Tool 1

Vulnerability scanners

Tools like Nessus or OpenVAS list the weaknesses on each machine and give each one a severity number out of 10 (a "CVSS score").

Tool 2

Firewalls

Decide which network connections are allowed and which are blocked.

Tool 3

SIEM systems

Collect and search security logs so analysts can spot suspicious activity after the fact.

They all share the same blind spot: each one looks at a weakness or an alert on its own. They can tell you machine A has a medium issue and machine B has a low issue — but not that those two issues, plus one reused password, chain together into a single path from the public web server straight to the customer database.

Two consequences

Severity ≠ real risk

A "critical" weakness on a machine no attacker can reach matters less than three "low" weaknesses that together form a working path to your crown jewel. Ranking by severity alone sends teams to fix the wrong things first.

Chaining doesn't scale by hand

A human could trace how weaknesses combine — but past a handful of machines the number of possible routes explodes. Nobody maps them manually.

ASCEND fills exactly this gap, for one focused slice of the problem: privilege escalation and lateral movement on Linux networks.

03 — The core move

The big idea: don't predict — prove

Other research in this area guesses: it reads scanner output and reasons that an attack path probably exists, or trains a model to predict risk. The weakness is that a guess can be wrong, and you never find out until a real attacker proves it for you.

ASCEND's one-line pitch "Prior work predicts. ASCEND proves." A path is only called "verified" when every single step of it was actually executed in the lab and every step worked.

So ASCEND doesn't just draw a diagram of possible attacks. It runs each proposed attack inside a safe, disposable copy of the network and watches whether it truly succeeds. That gives it something no scanner has: ground truth — facts from execution, not scores we invented.

How does it know a step really worked? Each target machine holds a secret marker — a canary — that only a genuinely successful attacker could reach or read. The step counts as a pass only if that canary is captured, not just because a script finished without an error. This stops the system from fooling itself.
04 — The vocabulary

The words you'll keep hearing

Everything else in this project is built out of these building blocks. Click any term to expand it.

Privilege escalation +
Going from a limited account to a more powerful one — ultimately to root, the Linux account that can do anything. This is the "climbing" ASCEND is named after. Example: a normal service account tricks a misconfigured program into running its command as root.
Lateral movement +
Moving sideways from one machine to another — e.g. logging into a second server using a password you stole from the first. Escalation climbs; lateral movement spreads.
Foothold & crown jewel +
The foothold is where the attacker starts — a low-value entry point like a public web server. The crown jewel is the thing worth protecting — the database with the sensitive data. ASCEND measures every route from one to the other.
MITRE ATT&CK & "techniques" +
A free, globally-used catalogue that gives every real attacker behaviour a standard code, like T1068. Using it means our scope is written in a vocabulary every security professional already recognises, instead of words we made up.
CVE → CWE → CAPEC → ATT&CK +
A chain of four public catalogues, from the specific to the general:
CVE — one specific named vulnerability (e.g. CVE-2021-4034).
CWE — the type of weakness it belongs to (e.g. "improper input validation").
CAPEC — the pattern an attacker uses to abuse that weakness.
ATT&CK — the attacker technique it corresponds to.
This chain is how ASCEND turns "this machine has CVE-2021-4034" into "this machine is exploitable via technique T1068." It's the backbone of the knowledge graph.
CVSS score +
The standard 0–10 severity number attached to each CVE. ASCEND's central argument is that CVSS alone is a poor guide to real risk, because it ignores whether a weakness is actually reachable and chainable.
SUID binary +
A program flagged to run with the privileges of its owner (often root) rather than whoever launched it. Useful when done right; dangerous when a program that can be made to run arbitrary commands is left SUID — it hands out root. One of our escalation vectors.
sudo misconfiguration +
sudo lets specific users run specific commands as root. A sloppy rule — e.g. letting a service account run a powerful command with no password — can be abused to become root outright.
Docker socket / container escape +
A container is a lightweight isolated box for running software. If a container can reach the host's "Docker socket," it can control the underlying machine — "escaping" its box. That's a jump from inside the sandbox to owning the host.
Credential reuse +
The same password or SSH key working on more than one machine. Find it once, and it unlocks the next host for free. This single bad habit is often the edge that joins two separate machines into one long attack path.
Chokepoint +
The heart of ASCEND. A weakness that many different attack paths all pass through. Fix one chokepoint and you break many paths at once — so chokepoints are the highest-value things to fix. Finding the fewest chokepoints that kill the most paths is the project's signature output.
Precision (the headline number) +
Of all the paths ASCEND proposed, what fraction actually worked when executed. It's how we grade the path-finder honestly — a proposed path that fails in the lab counts against us.
05 — The scope, locked

The seven attacker moves we study

A final-year project dies if it tries to do everything. ASCEND is deliberately narrow: privilege escalation and the lateral movement that supports it, on Linux, inside our own lab. These are the exact ATT&CK techniques in scope — and no others.

CodePlain-English moveHow it shows up in our lab
T1548.001Abuse a program that runs as root to run your own command as rootA misconfigured SUID binary
T1548.003Abuse an over-permissive sudo ruleA no-password sudo rule on a dangerous command
T1068Use a kernel bug to jump to rootPwnKit (CVE-2021-4034) & DirtyPipe (CVE-2022-0847)
T1611Break out of a container to control the host machineAn exposed Docker socket
T1021.004Log into another machine over SSH (move sideways)Using a harvested key to reach the next host
T1550Reuse a stolen credential or key somewhere elseThe same key works on a second machine
T1552.001Find a password or key left in a readable fileA key or secret in a world-readable file

The two anchor vulnerabilities

For the "kernel bug" move we anchor on two real, famous, well-documented vulnerabilities: PwnKit (a flaw in the pkexec tool) and DirtyPipe (a flaw in the Linux kernel's pipe handling). Both map cleanly to technique T1068, so the link to ATT&CK is real, not asserted. Neither runs in today's 3-container lab yet: DirtyPipe needs a genuinely vulnerable kernel (real VMs), and the PwnKit host is on the roadmap. Until then the lab reports the kernel step as not executable rather than faking it.

Explicitly out of scope (and we say so proactively): Windows & Active Directory, malware / phishing / denial-of-service, and anything run against real production systems. We use one web exploit only as the attacker's front door — we don't study web attacks themselves.
The sentence to say at the review "ASCEND does not detect all attacks. It answers one question well: given a foothold, what are all the ways an attacker escalates to our critical assets, which of them actually work, and what is the cheapest way to break them?"
06 — The mental model

Three graphs, not one

ASCEND thinks about the world as three separate maps. Keeping them separate is what makes the whole system clear.

Map 1 · public

Knowledge graph

Everything publicly known about vulnerabilities and attacker techniques — the CVE→CWE→CAPEC→ATT&CK chain plus description text. It's the same for everyone and rarely changes.

Map 2 · our lab

Environment graph

A map of our specific network: which machines exist, what accounts and credentials they hold, which machine can reach which, and what weaknesses each one has.

Map 3 · the routes

Attack-path graph

The routes an attacker can actually take through the environment, built by searching the environment graph from the foothold to the crown jewel.

The link that makes it work Every weakness in Map 2 is connected to a technique in Map 1. That single link is what upgrades a dry fact — "this host runs a vulnerable version of pkexec" — into a meaningful one: "this host is exploitable via technique T1068, and here's the public evidence why."
07 — End to end

How ASCEND runs, step by step

Read top to bottom — this is the whole system in order.

1

Collect the facts

Read-only probes inspect each lab machine — its users, sudo rules, SUID programs, kernel version, open ports and stored credentials — and write them down as structured facts.

2

Build the environment graph

Those facts become Map 2, with every weakness linked to its ATT&CK technique in the public knowledge graph (Map 1).

3

Enumerate the paths

A search algorithm starts at the foothold holding a growing set of machines, privileges and stolen credentials, and finds every route that reaches the crown jewel — with caps so it can't run forever, and duplicate routes collapsed.

4

Verify by execution

The attacker container actually runs each step in the lab. The per-host canary confirms real success or failure, with a recorded reason. This produces the headline precision number and a labelled record of what truly works.

5

Score exploitability (ML)

A machine-learning model learns to predict whether a step would succeed without running it — so the method can later assess a real network read-only. It must beat simple baselines or it gets dropped and we say so.

6

Find the chokepoints

The remediation engine computes the smallest, cheapest set of fixes that breaks the most paths — using a fast greedy method today. An exact optimal solver is planned, so we can measure how close the greedy one gets.

7

Prove the fix works

Apply a recommended fix in the real lab, re-run the whole thing, and confirm the paths through that weakness have vanished. Repeat until the crown jewel is unreachable.

The clinching momentStep 7 is the strongest thing to show a panel: the result is demonstrated, not claimed. You watch real attack paths disappear after a real fix.

09 — The plan

How we actually build it

The work splits into two phases. Phase 1 is the foundation and the real contribution; Phase 2 adds the machine learning and the remediation proof on top.

Phase 1 — Foundation

Build target: ~mid-January 2027
  • The isolated lab that rebuilds and resets in seconds
  • Read-only fact collectors (one record per host)
  • The public knowledge graph (CVE→CWE→CAPEC→ATT&CK)
  • The environment graph + the path enumerator
  • The execution verifier and its labelled dataset — the core contribution
  • A basic dashboard to show it all

Phase 2 — Scoring & remediation

Through to June 2027
  • The exploitability scorer (simple models first, fancy ones only if they earn it)
  • The chokepoint engine (greedy built; exact optimal planned)
  • The before/after proof loop — the signature result
  • Assessment mode: read-only scan of a real host (stretch goal)
  • The scripted demo and the research paper
The code maps 1:1 to this plan. Each piece is already a folder in the repo: collectors/, knowledge_graph/, environment_graph/, enumerator/, verifier/, chokepoint/, service/ (the API) and dashboard/ (the web app). Three people own three workstreams: the lab & ground truth, the graphs & ML, and the app & integration.
10 — Where it all happens, safely

The lab

Everything attack-related happens inside a self-contained practice network of Docker containers on a private connection with no route to the internet or the campus network — except one read-only download of public vulnerability data. Containers are used because they reset in seconds, and building the training dataset needs hundreds of reset-and-run cycles.

What it looks like today vs. the roadmap

Today (in code)

3-host container lab
  • web01 — entry foothold, low privilege
  • app01 — sudo + SUID escape, mid-value
  • db01 — the crown jewel (root, highest value)
  • Currently finds 2 paths; 1 verifies, 1 partial (precision ≈ 0.5)

Roadmap target

10 hosts incl. 2 real VMs
  • Extra hosts: a CI box (Docker-socket escape), an NFS box, an admin jump host, a second app host
  • Two full virtual machines so a real kernel exploit can run (containers share a kernel, so some kernel bugs can't be run for real in them)
  • Enables the 30+ lab variants needed to train the ML model properly
Safety, stated plainlyAttack scripts run only from the attacker host and live only inside the lab folder. No exploit code is ever shipped in the repository. The only outside access is that single, one-time, read-only pull of public vulnerability data. This is legitimate academic defensive-security research.
11 — Grading ourselves honestly

Proof & scoring — how we know it worked

A good project is measured, not asserted. ASCEND reports real numbers against real baselines:

Path-finder

Precision and recall — of the paths we proposed, how many work; of the paths that exist, how many we found.

Speed

How long enumeration takes (target: 95% of runs under 5 seconds).

Verifier reliability

How often a result flips between runs — goal: zero flakiness.

ML scorer

Accuracy and F1 on machines it never trained on — and it must beat three dumb baselines (always-guess-yes, "CVSS ≥ 7", and the scanner's own flag) or it's cut.

Remediation

How few fixes break the crown-jewel path, and how that compares to fixing in plain CVSS order or random order.

Reproducibility

Every table and figure is generated by a script from versioned settings with recorded random seeds.

Why "beat the baselines" matters. Any model can produce a number. The honest question is whether it beats the obvious shortcuts. If the ML scorer can't beat "just trust CVSS," we drop it and say so — because ASCEND's headline is execution-verified truth, not a model's self-reported accuracy.
12 — The "isn't this just X?" defence

What's actually new here

A review panel will ask how this differs from what already exists. The honest, narrow answer:

vs. BloodHound

BloodHound maps attack paths in Windows Active Directory; ASCEND targets Linux privilege escalation — a different, less-tooled domain. BloodHound also only shows paths; it doesn't verify them by execution or compute an optimal fix set. ASCEND adds both.

vs. logical attack-graph tools (e.g. MulVAL)

These reason logically from scanner output to a graph of possible attacks, but generally don't execute them to confirm, and don't learn which weaknesses are truly exploitable. ASCEND's execution-grounded proof and learned scoring are the difference.

vs. the base research papers

We borrow good ideas — attaching vulnerability description text to graph nodes, and correlating evidence against a graph — but add what neither has: execution-verified ground truth for privilege-escalation paths plus a remediation-optimisation output.

The claim, kept modest on purpose"We don't claim novelty over the whole field. We claim one specific, defensible combination: prove the paths by running them, then compute the fewest fixes that kill the most of them — and prove the fixes work."
