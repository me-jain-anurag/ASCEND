The repo at a glance

02 — The one idea the whole codebase is shaped around

The golden rule: observe, judge, prove — separately

This is the single most important thing to understand about the code. Every layer is deliberately split into three jobs that are kept in different places, so you can always answer "why does ASCEND believe this?" by reading one small piece.

Observe

Probes just report

A probe measures a raw fact and never decides what it means.

"file mode 0644, owner www-data, contains a private key"
Judge

One rule decides

Whether that raw fact is a weakness is decided in one rule in scope.yaml plus one function in derive.py.

"0644 on a key = disclosure → vector T1552.001"
Prove

The verifier tests it

The verifier goes back into the lab and runs the step to see if the judgement was right.

"we read the root-only canary → it really worked"
Why this mattersEverything up to the enumerator is reasoning ("the door looks unlocked"). The verifier is reality ("we walked through it, here's the output"). That split is the project's argument — and in the code it means a probe never makes a claim and an adapter never grades its own result.

A guiding motto you'll see honoured everywhere: "we'd rather show a zero than a placeholder." If something can't be verified, it's reported as unverified with the reason — never quietly rounded up.

03 — The control panel

scope.yaml — one file that drives everything

Rather than scatter decisions across the code, ASCEND puts them in a single config file. Every other module reads it. It has five parts:

SectionWhat it definesWho reads it
techniquesThe 7 ATT&CK techniques, each tied to the probe that detects itcollectors, enumerator
rulesThe exact condition that turns a raw reading into a weakness (e.g. "kernel below 5.16.11 = DirtyPipe")derive.py
inventoryBusiness facts no scan can find: each host's role and asset valuederive.py
remediationThe fix templates and their effort cost (1 = minutes … 5 = change control)chokepoint/engine.py
verifierWhat the verifier is allowed to run, and where the canary livesverifier/
This is why the project is auditable: to challenge any finding, you read one rule here and one function in derive.py. Nothing is hidden in the depths of the code.
04 — The practice network

lab/ — three machines, on purpose vulnerable

The lab is defined in lab/docker-compose.yml: three Linux containers on two private networks with no internet route. The two-network layout is deliberate — app01 sits on both, so it's the only bridge between the entry point and the crown jewel.

# [ dmz network ]            [ core network ]
  web01  ──►  app01  ──►  db01
  entry      (pivot)     CROWN JEWEL

# web01 and db01 share NO network — they cannot reach each other.
# The collector discovers this by trying real TCP connections.

What's planted on each host

HostPlanted weaknessTechnique
web01An SSH private key readable by everyoneT1552.001
app01appuser may run tar as root with no passwordT1548.003
app01+db01The same key opens both machines (credential reuse)T1550
db01A setuid-root findT1548.001
db01A kernel declared vulnerable to DirtyPipeT1068
Negative controls are planted too. Each host's kernel version is set on purpose: db01 runs 5.16.0 (vulnerable), but app01 runs a patched 5.10.150. A naïve "old kernel = vulnerable" check would wrongly flag app01 — the rule has to be smart enough to decline it. Having weaknesses that are not findings is how you prove the rules actually discriminate.
An honest limitation baked into the labContainers share the host machine's real kernel, so db01 can't actually run the vulnerable 5.16.0 kernel the graph says it has. That's why the DirtyPipe step is reported as "not executable" rather than faked — and why a true kernel exploit needs real virtual machines later (see §14).
05 — Looking at the machines

collectors/ — 9 probes that observe, 1 file that judges

Nine small probes each read one kind of fact off every host. They only report; none of them decides anything.

ProbeReads
accounts.pyuser accounts and their privilege
sudo.pysudo rules
suid.pysetuid-root programs
ssh_keys.py / cred_files.pySSH keys and secrets left in readable files
kernel.pythe (declared) kernel version
docker_socket.pyan exposed Docker socket
ports.py / reachability.pyopen ports and which host can reach which

Then derive.py (the judge) turns those raw readings into weaknesses — only when a rule in scope.yaml says so — and writes the result to environment_graph/facts.json. Two details make the output evidence, not assertion:

1

Credential reuse is proven cryptographically

Every private key found is fingerprinted (SHA256) and matched against every authorized_keys on every host. "This same key opens two machines" is a hash match in sshkeys.py — not a guess from filenames.

2

Reachability is measured, not declared

reachability.py opens real TCP connections between hosts. That's how it discovers that web01 can't reach db01 — nobody writes that into a config.

Each fact also carries its provenance: observed (a probe measured it) or declared (an operator supplied it, like host roles or the simulated kernel). You always know whether a fact came from a scan or from a human.

06 — The two reference files

The knowledge graph & the environment graph

These are the two "maps" from the explainer, and in the code they're just two JSON files:

A

knowledge_graph/pack.json — public knowledge

The CVE → CWE → CAPEC → ATT&CK reference data, restricted to our 7 techniques. It's what lets the collector attach a proper name and lineage to each finding (e.g. tying a kernel version to CVE-2022-0847 → technique T1068).

B

environment_graph/facts.json — our lab

The output of the collector: every host, account, credential, reachability edge and weakness ("vector") in the lab, each linked to its technique. This is the one file the enumerator, the service and the chokepoint engine all read.

There's also facts.sample.json — a hand-written example in the same format. It means the enumerator and dashboard can be demoed even without building the lab, and it keeps the schema honest (the real collector output must match it byte-for-byte).
07 — Finding the routes

enumerator/pathfinder.py — the route search

This is the "find every climbing route" step. It's a state-space search: instead of asking "where is the attacker?", it tracks "what does the attacker hold?" — which machines (at which privilege) and which stolen credentials. From the entry foothold it grows that set one legal move at a time, and every sequence that ends at root on the crown jewel is a path.

There are exactly three kinds of move

1

Harvest

Pick up a credential from a readable file (a credential_access vector).

2

Move

Log into another machine using a credential you hold and can reach over the network. This is the one that needs both a working key and reachability — which is why key reuse and network segmentation interact.

3

Escalate

Become root on a machine you already have a foothold on (sudo / SUID / kernel exploit).

Worth knowingThe pathfinder has zero third-party dependencies — pure standard-library Python. It's the fallback that still runs when everything else breaks. It also writes two outputs: eval/analysis.json (for the API) and dashboard/data.js (for a no-server view).

One subtlety the code is careful about: the pathfinder reports two separate numbers — config coverage ("every step's weakness is present") and precision ("every step was proven by execution"). Only the verifier can raise precision above zero, so on its own the pathfinder honestly reports precision = 0.

08 — Proving it for real

verifier/ — the part that makes the numbers trustworthy

The hard part isn't running an attack — it's knowing whether it truly worked (exit codes lie, attacks half-succeed). The verifier solves this with one mechanism applied identically to every technique: the canary.

The canaryEvery host carries a file readable only by root, containing a random secret regenerated on each build. Every escalation ends by trying to read it. If the secret comes back, you were root. If it doesn't, you weren't. One rule, every technique — so results are comparable.

Three outcomes, never two

This is the detail that keeps the verifier honest:

OutcomeMeaning
escalatedran, and privilege genuinely increased
not_escalatedran, and it did not work — a real negative result
not_executablenever ran — the lab can't meet a precondition (e.g. the real DirtyPipe kernel)

Collapsing "didn't work" and "couldn't be tried" into one would turn a lab limitation into false evidence that an attack fails. So a route containing an un-runnable step is marked partial — not proven, and not disproven.

How the pieces fit

1

runner.py — the loop

Reset the host to a clean, unprivileged state → run the technique → read the canary → record the outcome. It also guards against meaningless results (e.g. refusing to "escalate" from an account that's already root).

2

adapters/ — one per technique family

config_abuse.py (sudo / SUID / readable key), lateral_ssh.py (the SSH hop), and anchor_cve.py (the kernel exploit). An adapter's only job is to trigger the technique — it must decide success through signal.py, never its own exit code.

3

outcomes.jsonl — the labelled dataset

Every run is appended here. This growing file of proven/failed labels is exactly what the future ML scorer will train on — producing it is why the verifier exists.

A cautionary tale the code now guards againstThe lab once shipped a "DirtyPipe exploit" that was really just a setuid-root program calling setuid(0) — it returned root because of its file permissions, on any kernel, and the verifier happily marked the CVE "verified." Removing the setuid bit made it fail on an unchanged kernel, proving the "verification" was measuring a file mode, not an exploit. This is why the repo ships no exploit code, and a test fails the build if any appears.
09 — The fewest fixes

chokepoint/engine.py — fixes ranked by routes killed

This answers the question the demo turns on: which few fixes kill the most routes? It uses greedy weighted set-cover — repeatedly pick the fix with the best routes-killed-per-unit-of-effort until every route is covered.

The crucial design choice: measured, not inferredIt would be easy to just count how many routes mention a weakness. Instead, the engine removes the fix from a copy of the facts and re-runs the real enumerator, then compares. So "this fix eliminates these 3 routes" is produced the same way the dashboard's Apply button proves it live — the prediction and the demonstration can't disagree.

It also considers a second kind of fix that a weakness-only view would miss: revoking a reused credential everywhere it's accepted, without even touching the file it leaked from — often the cheapest fix of all.

10 — Tying it together & showing it

service/ & dashboard/

service/main.py is a FastAPI web server (~830 lines) that exposes the whole pipeline as JSON endpoints:

EndpointDoes
GET /api/networkthe host-and-reachability map
POST /api/enumeraterun the pathfinder, return the routes
POST /api/verifyrun a route for real in the lab (the Verify button)
GET /api/remediationthe ranked fix plan
POST /api/remediation/applyapply a fix and re-check (the Apply button)
GET /api/status · POST /api/resetcurrent state · reset the lab

dashboard/ is a React + Vite + TypeScript app with four tabs — Overview, Network, Paths, Remediation — backed by components NetworkGraph, PathList, RemediationPanel and Sidebar. It's what an analyst actually looks at.

11 — Keeping it honest

tests/ — 42 checks, including anti-lying checks

There are 42 automated tests across tests/test_pipeline.py and the verifier's own tests. Beyond ordinary correctness, some exist specifically to protect the project's integrity:

  • A test that fails the build if anything claims an execution that never happened.
  • A test that the repository contains no exploit code.
  • Tests that each in-scope technique resolves to a real ATT&CK entry, and that the rules correctly decline the planted negative controls.

These encode the principles from §2 as things a machine checks on every change, not just promises in a document.

14 — Honest about the gaps

What's not built yet

The code is upfront about its edges — nothing here is faked in the meantime:

1

The ML scorer planned

The model that predicts exploitability without running the attack. Its training data — outcomes.jsonl — is exactly what the verifier produces, so the foundation is in place; the model folder isn't written yet. This is the heart of Phase 2.

2

A real kernel exploit planned

Running DirtyPipe for real needs a genuinely vulnerable kernel, which means virtual machines instead of containers. Until then T1068 is correctly reported as not_executable.

3

Syscall telemetry planned

verifier/telemetry.py is an interface with no monitoring tool (Falco) behind it yet — so evidence says not captured rather than inventing a log line.

4

Credential staging between hops planned

A lateral hop is only verifiable where the key already sits on the source host; carrying a harvested key forward between hops isn't automated yet.

This matches the plan exactly: Phase 1 (the whole foundation) is built and runs; Phase 2 (the ML scorer, built on the verifier's data) is the road ahead.
